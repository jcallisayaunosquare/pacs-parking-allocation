    01Executive Summary

    The whole system in two minutes: what it does, the six decisions that shape it, and how we will know it worked.

    A residential building has fewer parking spots than residents who want one. Today that is settled by whoever asked first, by seniority, or by argument. PACS replaces that with a quarterly weighted raffle whose outcomes are recorded permanently, whose odds visibly favour whoever has waited longest, and whose every draw can be replayed and verified after the fact.

    The six decisions that shape everything else

    Decision 01
    Fairness as stored state, not a report

    Each resident carries a score that rises every cycle they miss and resets when they win. Draw weight is score + 1. It is a table, not a query — so it can be shown to the resident, audited, and reasoned about.

    Decision 02
    Every draw is reproducible

    The random seed is stored with the run. Anyone can replay a historical raffle and get the same winners. Fairness that cannot be verified is only a claim.

    Decision 03
    The database enforces the invariants

    "One spot per resident per cycle" is a unique constraint, not a code path. A logic bug becomes a failed transaction instead of a duplicate allocation.

    Decision 04
    One run at a time, guarded twice

    A partial unique index makes a second concurrent run impossible; the per-cycle constraints catch it again if the first guard is ever bypassed.

    Decision 05
    Notifications can never break a raffle

    Events go to an outbox inside the raffle transaction and are relayed afterwards. A mail outage delays notices; it cannot undo an allocation.

    Decision 06
    Domain first, cloud second

    The domain names capabilities, not vendors; §10 then binds them to AWS serverless (Lambda, API Gateway, Cognito, RDS) with a cost model in hand. Clean Architecture keeps that binding in the outer ring only.

    Explicitly out of scope for v1

    Naming what we are not building is as useful as naming what we are — each of these has been considered and deliberately postponed.

    Payments

    No fees, billing or deposits. If parking becomes paid, that is a new bounded context, not a column on resident.

    Guest parking

    Visitor spots are a different allocation problem — short-lived, first-come — and would distort the fairness model.

    Spot preferences

    No "I want level B2". Introduces matching complexity and disputes; revisit only with evidence residents care.

    Swaps between residents

    Peer-to-peer trades undermine the audit trail. Release to the waitlist is the supported path.

    Live occupancy

    Requires sensors or cameras. Groundwork only — see the plate recognition section.

    Native mobile apps

    A responsive web client covers the four screens residents actually use.

    If you read nothing else

    The three things most likely to go wrong are concurrency during the run, a stale cache showing the wrong allocation, and residents not believing the draw was fair. Each has an owner in the risk register, a control in the design, and a test that proves the control works.

    02Scope & Reading Guide

    PACS (Parking Allocation Context System) manages a finite pool of parking spots in a residential building. Residents opt in; every three months the system runs a raffle that allocates spots, weighted so that residents who have gone longest without a spot are most likely to win. Every outcome is recorded permanently, and that history is the input to the next raffle. The loop is the product.

    04Actors & Stakeholders

    PRIMARYResident

    Registers for a cycle, checks current status and next allocation date, reads own history, releases a spot. Sees only their own data.

    PRIMARYBuilding Admin

    Manages residents, eligibility and the spot inventory; opens and closes cycles; triggers and audits runs; reads fairness metrics.

    SYSTEMScheduler

    A non-human actor. Opens registration, closes it, executes the quarterly run, expires assignments.

    SYSTEMNotifier

    Sends registration-open, win, waitlist and expiry notices. Consumes domain events, never called inline.

    FUTURELPR Camera

    Plate-recognition edge device. Reports observed plates at entry/exit. See §24 — not built in phase 1.

    SUPPORTAuditor

    Reads immutable history to verify the raffle was fair. Read-only; may be the HOA board rather than a user role.

    05Use Cases

    Expanded specification — the three that carry the system

    UC-05 · Execute allocation run

    ActorsBuilding Admin (manual) or Scheduler (automatic)
    PreconditionsCycle exists in state REGISTRATION_CLOSED; no run is RUNNING; at least one active spot exists
    Main flow1. Acquire the exclusive run lock. 2. Create run in RUNNING. 3. Snapshot registrations, eligible residents, fairness scores and the active spot pool. 4. Pre-assign accessible spots to residents with an accessibility need. 5. Weighted draw without replacement over the remainder. 6. Persist assignments, waitlist and history inside one transaction. 7. Recompute fairness state. 8. Mark run COMPLETED, emit AllocationCompleted. 9. Release lock.
    Alternate A1A run is already in flight → reject with 409 RAFFLE_IN_PROGRESS; no state change.
    Alternate A2Registrations ≤ spots → everyone wins; surplus spots stay available; waitlist empty.
    Alternate A3Zero registrations → run completes as COMPLETED_EMPTY; admin is notified; no fairness change.
    Exception E1Failure at any step → transaction rolls back, run marked FAILED with the error, lock released, nothing partially assigned.
    PostconditionsEvery registration has exactly one outcome row (ASSIGNED / WAITLISTED); fairness scores reflect the outcome; the run is reproducible from its stored seed.

    UC-08 · Register for the raffle

    ActorResident
    PreconditionsAuthenticated; is_eligible = true; a cycle is in REGISTRATION_OPEN
    Main flowResident opens the dashboard → sees the open cycle and the closing date → confirms registration → system stores the registration and returns the projected fairness weight and current registrant count.
    AlternatesAlready registered → idempotent 200 with the existing registration. Ineligible → 403 NOT_ELIGIBLE plus the admin-supplied reason. Registration window closed → 409 REGISTRATION_CLOSED with the next cycle's opening date.
    PostconditionsOne registration row for (cycle, resident); resident's cached status invalidated.

    UC-09 · View current parking status

    ActorResident
    PreconditionsAuthenticated
    Main flowThe dashboard returns, in one call: current assignment (spot code, level, valid-until) or waitlist position; the next cycle's key dates; the fairness score with a plain-language explanation; and the last four outcomes.
    NotesThis is the single hottest read in the system — it is what every resident opens. It is served from cache and invalidated by run completion, release and registration events (§20).

    Acceptance criteria — executable form

    Feature: Fairness-weighted allocation

  Scenario: Fewer spots than registrants
    Given 50 registered residents with distinct fairness scores
    And 30 active parking spots
    When the allocation run executes
    Then exactly 30 residents hold exactly one spot each
    And no spot appears in two assignments
    And the remaining 20 residents occupy waitlist positions 1..20
    And every one of the 50 has exactly one history row for this cycle

  Scenario: Fairness actually favours the long-waiting
    Given resident A has missed 4 consecutive cycles (score 4)
    And resident B has missed 0 cycles (score 0, just won last cycle)
    When 10000 simulated runs execute with 1 spot and only A and B registered
    Then A wins in at least 75% of runs
    And B wins in at least 1% of runs      # never a hard exclusion

  Scenario: Concurrent triggers cannot double-allocate
    Given an allocation run is in progress
    When a second run is triggered for the same cycle
    Then it is rejected with error code RAFFLE_IN_PROGRESS
    And the number of assignments for the cycle is unchanged

  Scenario: Score update after the run
    Given resident A was assigned a spot and resident B was waitlisted
    When the run completes
    Then A's fairness score is 0 and A's total_wins increased by 1
    And B's fairness score increased by exactly 1

  Scenario: A mid-run failure leaves nothing behind
    Given the persistence step fails after 12 of 30 assignments
    When the transaction aborts
    Then zero assignments exist for the cycle
    And the run status is FAILED with a recorded error
    And the run lock is released

    Why these numbers

    A residential building is a small-data problem — hundreds of rows, not millions — so the binding constraints are correctness and trust, not throughput. NFR-05 and NFR-06 are therefore the requirements worth spending architecture on; NFR-01's two-second budget is generous on purpose, because the run happens four times a year and being right matters far more than being fast.

    Architecture decision records

    ADRDecisionRejected alternativesWhy
    ADR-001Relational store as the source of truthDocument / key-value storeThe invariants that matter (one spot per resident per cycle, no partial runs) are multi-row and transactional. A unique constraint is a stronger guarantee than application code, and the data volume is trivially small.
    ADR-002Modular monolith, not microservicesService-per-moduleSix modules sharing one transaction boundary; the raffle would otherwise need a distributed transaction to stay correct. Module boundaries are enforced in code so a split later is mechanical.
    ADR-003Asynchronous notifications via an outbox + event busInline sending during the runSatisfies FR-24: a mail gateway outage must not roll back an allocation. Also keeps the run transaction short, which matters for lock hold time.
    ADR-004Delegated identity, token-basedHome-grown users/passwords tablePassword storage, reset flows and MFA are high-risk to build and free to rent. PACS stores a subject id, never a credential.
    ADR-005SPA client, static-hostedServer-rendered appThe product is an authenticated dashboard: no SEO need, no first-paint-critical public content. Static hosting also removes a whole tier from the ops surface.
    ADR-006Seeded, reproducible drawUnseeded RNGFairness that cannot be audited is only a claim. Storing the seed lets anyone replay a historical run and verify the outcome — the single strongest trust feature in the product.
    ADR-007Cache is read-only and disposableWrite-through / cache-as-storeEvery cached value is recomputable from the store. A cold cache costs latency, never correctness.
    ADR-008Logical design before cloud mappingDesigning against specific services from day oneKept the domain vendor-neutral and the comparison honest. The mapping is now made in §10 (ADR-011 … ADR-018); it lives only in the infrastructure ring, so it costs one adapter per platform seam.

    12The Allocation Engine

    This is the component the whole product is judged on. Everything else is CRUD.

    Fairness model

    Each resident carries a score s. After every run in which they participated:

    assigned  → s := 0,        consecutive_misses := 0,  total_wins += 1
waitlisted→ s := s + 1,    consecutive_misses += 1
not registered / ineligible → s unchanged        (FR-21)

    Draw weight is w = s + 1. The +1 matters: a resident who just won still has a non-zero chance next quarter, which keeps the process a lottery rather than a strict rotation. The weight is linear on purpose — it is explainable to a resident in one sentence: "every quarter you miss, your name goes in the hat one more time."

    Should the weight be capped (say at 12, three years of misses) so one very unlucky resident cannot come to dominate a small pool? And should the growth be linear or super-linear? This is a business decision, not an engineering one — it is isolated behind DrawStrategy precisely so the HOA can change its mind without a rewrite.

    Execution flow

    The draw, in code

    /**
 * Weighted lottery without replacement.
 * Deterministic for a given (entrants, seed) pair — this is what makes a run auditable (ADR-006).
 * Complexity: O(n log n) to sort + O(k log n) to draw k winners via a Fenwick tree over weights.
 */
function drawWinners(entrants, spotCount, seed) {
  const rng = seededRng(seed);                        // xorshift128+ — stable across runtimes
  const pool = [...entrants].sort(byResidentId);      // stable order, or the seed means nothing
  const weights = new FenwickTree(pool.map(e => e.fairnessScore + 1));

  const winners = [];
  const k = Math.min(spotCount, pool.length);

  for (let i = 0; i < k; i++) {
    const target = rng.nextFloat() * weights.total();  // uniform in [0, totalWeight)
    const idx = weights.findByPrefixSum(target);       // O(log n)
    winners.push(pool[idx]);
    weights.set(idx, 0);                               // remove — no replacement
  }
  return winners;
}

    Three properties this gives us, each directly testable:

    • Reproducible — same seed and same entrant set always yields the same winners, so any resident can be shown exactly why they lost.
    • Proportional — over many runs, win frequency tracks (s+1) / Σ(s+1). Verified by the 10 000-run statistical test in §06.
    • No starvation — every weight is ≥ 1, so no participant's probability is ever zero.

    Why not strict rotation, given it scores best

    Because the residents are not a fixed set. People move in and out, lose and regain eligibility, and skip cycles. A queue must then answer "where does a returning resident go?" — and every answer is a policy argument waiting to happen. A score-weighted draw degrades gracefully: a newcomer simply starts at weight 1, and someone who skipped two cycles does not silently bank credit for them (FR-21). The weighted lottery buys robustness against a messy real world at the cost of two extra cycles of worst-case waiting.

    The arithmetic, stated exactly

    Draw probability for one slot 
    P(resident i wins the next slot) = w_i / Σ w_j        where w = fairness_score + 1
                                                     and j ranges over remaining entrants

After each slot the winner's weight is removed (drawing without replacement),
so the odds for everyone still in the hat rise for the following slot.

Score transition after a run the resident participated in:
    assigned    → score = 0
    waitlisted  → score = score + 1
    skipped     → score unchanged        (ineligible or withdrew — see FR-21)

    Two properties worth stating because they are what residents actually ask about:

    • Nobody is ever excluded. Minimum weight is 1, so the probability of winning is never zero — even for someone who won last quarter.
    • Nobody can game it. The only way to raise your weight is to not win, and the draw order is fixed by a seed recorded before any winner is known.

    Rules the team holds to

    Events are facts, not commands

    Named in the past tense. A producer never knows or cares who consumes them, and never waits for a reply.

    Payloads carry ids, not PII

    Names, emails and plates stay in the database. A consumer that needs them reads them under its own permissions — so an event log is never a shadow copy of resident data.

    Additive versioning

    New optional fields do not bump version. Removing or retyping a field does, and both versions are published until every consumer has moved.

    Retry, then quarantine

    Five attempts with exponential backoff, then the message goes to a dead-letter queue that is alarmed. A poison message never blocks the queue behind it.

    The genuine conflict, stated openly

    Append-only history (NFR-06) and the right to erasure pull in opposite directions. Deleting a resident's rows would silently change the historical record and break the reproducibility of past runs — the property the whole trust argument rests on. Pseudonymisation is the resolution: the run stays replayable and the row counts stay intact, while the person becomes unidentifiable. This needs sign-off from legal, and it is why the schema keeps identity in resident and never copies names into allocation_history.

    Privacy by design, as built

    Minimisation

    No phone number, no ID document, no date of birth, no employer. Every field in §11 is there because a use case needs it.

    No PII in transit sideways

    Domain events carry ids only. Logs carry ids only. A plate appears in a log line only masked.

    Purpose separation

    Plate observations, when they exist, live in their own store with their own access control — they are not joined into the allocation database by default.

    Access is logged

    An admin reading a resident's record writes an audit row. Curiosity is visible; that alone changes behaviour.

    Breach response

    1. Contain — revoke the compromised credential or key, rotate secrets, block the path.
    2. Assess — from the audit and access logs, determine exactly which records were reachable and whether they were read.
    3. Notify — the supervisory authority within 72 hours where the regime requires it, and affected residents without undue delay when there is real risk to them.
    4. Remediate and record — fix the cause, add the regression test, write the post-incident review. The review is blameless and is published to the team.

    The contact chain, notification templates and authority details belong in the runbook (§21) — written before they are needed, because nobody drafts a good breach notice at 2 a.m.

    Runbooks

    RB-01 · An allocation run failed

    Symptom. AllocationFailed event, run row in state FAILED with error_detail, cycle still REGISTRATION_CLOSED.

    What is already safe. The transaction rolled back: there are no partial assignments and no fairness scores were changed. Residents see "the draw has not run yet", which is true.

    1. Read error_detail and the logs for that runId.
    2. Confirm the blast radius: SELECT count(*) FROM spot_assignment WHERE cycle_id = … must be 0.
    3. Verify the lock is released — no row with state = 'RUNNING'. If there is one, go to RB-02.
    4. Fix the cause. The three seen in testing: no active spots (inventory error), a database connection drop (retry), a migration mid-flight (never deploy during the run window).
    5. Re-trigger with a new idempotency key. A new run row and a new seed are correct — the failed draw was never revealed to anyone.
    6. Confirm entrant and spot counts match expectations, then tell the admin it is done.

    Do not hand-insert assignments. The constraint set is the only thing keeping the invariants true, and a manual insert bypasses the fairness update.

    RB-02 · A run is stuck in RUNNING

    Symptom. A run has been RUNNING past the timeout; every new trigger returns 409 RAFFLE_IN_PROGRESS.

    Cause. The process died between claiming the lock and committing — the row survives, the worker does not.

    1. Confirm nothing is actually working: no active database session for that run, no recent log lines.
    2. Confirm no assignments exist for the cycle. If any exist, stop and escalate — this is RB-03.
    3. Mark the run failed, which releases the lock: UPDATE allocation_run SET state='FAILED', finished_at=now(), error_detail='reaped: worker lost' WHERE id=…
    4. Re-trigger as in RB-01.
    5. File a ticket: the reaper job that should have done this automatically did not, or does not exist yet.
    RB-03 · An allocation is wrong and must be reversed

    Symptom. A duplicate assignment, an ineligible winner, or a run executed against the wrong cycle. Rare, serious, and the one operation the system deliberately makes hard.

    Principle. We do not delete history. We record a correction, so the record shows both what happened and that it was put right.

    1. Freeze: set the cycle to a state that blocks further changes and tell the admin to announce a hold. Residents finding out from each other is worse than the error.
    2. Capture evidence: export the run, its assignments and its history rows before touching anything.
    3. Revoke the affected assignments through the normal admin path, with a reason — this emits AssignmentRevoked and writes audit rows.
    4. Decide with the HOA: re-run the whole cycle, or repair only the affected slots from the waitlist? Re-running changes outcomes for people who did nothing wrong, so prefer targeted repair.
    5. Correct fairness state explicitly: anyone whose outcome changed needs their score recomputed from history, not hand-edited.
    6. Communicate to every affected resident, naming what happened, why, and what changed for them.
    7. Post-incident review within a week; the regression test lands before the next cycle.
    RB-04 · Residents report the wrong status

    Symptom. "The app says I'm waitlisted but I got the email saying I won." Almost always a stale cache (R-05), not a wrong allocation.

    1. Check the source of truth first: query the assignment directly for that resident and cycle.
    2. If the database is right, it is a cache problem. Confirm with cache_hit_ratio and the invalidation logs for AllocationCompleted.
    3. Immediate fix: flush the affected dashboard:* keys. Data is recomputable, so this is safe.
    4. Root cause: find the path that changed data without emitting the event, and add the missing invalidation to the event handler — never as an ad-hoc call in a service method.
    5. If the database is wrong, this is RB-03.

    The raffle does not need to get faster — it needs to get smaller. Allocation is naturally partitioned by building: two buildings never compete for the same spot. Keeping the run scoped to a building turns the hardest-looking scale problem into embarrassing parallelism, and it costs one column today.

    Deliberately not doing yet

    • Splitting into microservices — six modules that share one transaction. Revisit if team size or deploy cadence, not load, demands it.
    • Read replicas — the read volume is a few requests per second. Add one when metrics queries start competing with writes, which is a Stage 2 problem.
    • Event sourcing — the append-only history already gives the audit trail that is the real requirement, without the operational weight.
    • Real-time push — polling on a dashboard is fine when state changes four times a year. Worth revisiting only alongside §24, where events are genuinely continuous.

    Branching

    Pipeline

    Database migrations: expand, migrate, contract

    Migrations run separately from deploys and must be backward compatible for one release, so that a rollback does not meet a schema it cannot read.

    Renaming a column without downtime 
    Release N      EXPAND    add the new column, nullable; write to both; read the old
Release N+1    MIGRATE   backfill in batches; switch reads to the new column
Release N+2    CONTRACT  stop writing the old column; drop it

Rules
  · every migration has a tested down-script, or a documented reason it cannot
  · no migration runs inside the quarterly run window
  · batched backfills, never a single UPDATE over the whole table
  · rehearsed on a production-shaped copy before it runs for real

    Release checklist

    • CI green on the exact commit being tagged
    • Migrations rehearsed on staging, down-script verified
    • Smoke suite passing on staging against the same artefact
    • No cycle currently in REGISTRATION_CLOSED awaiting a run
    • Changelog written in language the building admin can read
    • Rollback owner named and available for the next two hours
    • Feature flags for anything half-finished — dark by default

    Rollback

    Redeploy the previous artefact; it is immutable and still in the registry, so this is a minute, not a rebuild. Schema stays put — that is what the expand/contract discipline buys. If a bad release wrote bad data, rolling back the code does not fix it: that is RB-03, and it is a different, slower procedure with human decisions in it.

    24Future Module — License Plate Recognition

    Not built in phase 1. Analysed here because the phase 1 schema and API must not make it expensive later — and because how a team would break this down is itself part of the deliverable.

    Target capability

    Cameras at the garage entrance and exit read plates. The system matches each plate to a registered vehicle, checks whether that resident holds a valid assignment right now, and records an occupancy event. Outcomes: automatic detection of unauthorised parking, live occupancy figures, and gate automation.

    What phase 1 does to make this cheap

    Groundwork shipped nowWhy
    vehicle table with normalised, unique platesThe join target for every recognition event. Costs almost nothing now; is a migration with data backfill later
    A query answering "does resident X hold a valid assignment at time T?"The authorisation check the pipeline needs, already indexed
    Event outbox and worker already in placeOccupancy events reuse the existing async path instead of inventing one
    Plate treated as PII from day one (§18.4)Retention and masking rules are already written when volume arrives

    Q-10Buy a recognition service or run our own model? Accuracy against local plate formats and night conditions decides it.Cost model, edge hardware spec

    How the collaboration is sequenced

    1. Spike, 1 week — the ML team benchmarks two candidate approaches on real footage from this garage; the lead specifies the ingestion contract in parallel. Exit: an accuracy number and a frozen schema.

    3. Integration, 1 week — real camera into staging, measure end-to-end accuracy and latency, tune the confidence threshold with the admin who will actually work the review queue.
    4. Shadow mode, 2 weeks — runs in production recording events but taking no action. Compares its judgements against reality before anything is enforced.
    5. Enable — only after shadow-mode precision clears the agreed bar, and only with a human in the enforcement loop (Q-14).
