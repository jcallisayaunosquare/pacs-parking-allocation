    01Executive Summary

    The whole system in two minutes: what it does, the six decisions that shape it, and how we will know it worked.

    A residential building has fewer parking spots than residents who want one. Today that is settled by whoever asked first, by seniority, or by argument. PACS replaces that with a quarterly draw whose outcomes are recorded permanently, in which whoever has waited longest goes first and the raffle only breaks an exact tie, and whose every draw can be replayed and verified after the fact.

    The six decisions that shape everything else

    Decision 01
    Fairness as derived fact, not stored state

    A resident's standing is not a column. It is the draw instant minus an anchor — the later of "made eligible" and "last bay stopped counting" — so there is no counter to drift and no job to fail. The longest wait goes first; history breaks a tie; the raffle only breaks an exact tie. What is stored is the key as computed, per entrant per run, because that is the record a resident may contest.

    Decision 02
    Every draw is reproducible

    The random seed is stored with the run. Anyone can replay a historical raffle and get the same winners. Fairness that cannot be verified is only a claim.

    Decision 03
    The database enforces the invariants

    "One spot per resident per cycle" is a unique constraint, not a code path. A logic bug becomes a failed transaction instead of a duplicate allocation.

    Decision 04
    One run at a time, guarded twice

    A partial unique index makes a second concurrent run impossible; the per-cycle constraints catch it again if the first guard is ever bypassed.

    Decision 05
    Notifications can never break a raffle

    Events go to an outbox inside the raffle transaction and are relayed afterwards. A mail outage delays notices; it cannot undo an allocation.

    Decision 06
    Domain first, cloud second

    The domain names capabilities, not vendors; §10 then binds them to AWS serverless (Lambda, API Gateway, Cognito, RDS) with a cost model in hand. Clean Architecture keeps that binding in the outer ring only.

    Explicitly out of scope for v1

    Naming what we are not building is as useful as naming what we are — each of these has been considered and deliberately postponed.

    Payments

    No fees, billing or deposits. If parking becomes paid, that is a new bounded context, not a column on resident.

    Guest parking

    Visitor spots are a different allocation problem — short-lived, first-come — and would distort the fairness model.

    Spot preferences

    No "I want level B2". Introduces matching complexity and disputes; revisit only with evidence residents care.

    Swaps between residents

    Peer-to-peer trades undermine the audit trail. Release to the waitlist is the supported path.

    Live occupancy

    Requires sensors or cameras. Groundwork only — see the plate recognition section.

    Native mobile apps

    A responsive web client covers the four screens residents actually use.

    If you read nothing else

    The three things most likely to go wrong are concurrency during the run, a stale cache showing the wrong allocation, and residents not believing the draw was fair. Each has an owner in the risk register, a control in the design, and a test that proves the control works.

    02Scope & Reading Guide

    PACS (Parking Allocation Context System) manages a finite pool of parking spots in a residential building. Residents opt in; every three months the system runs a draw that allocates spots in order of waiting time, so that whoever has gone longest without one goes first. Every outcome is recorded permanently, and that history is the input to the next draw. The loop is the product.

    05Use Cases

    Expanded specification — the three that carry the system

    UC-05 · Execute allocation run

    ActorsBuilding Admin (manual) or Scheduler (automatic)
    PreconditionsCycle exists in state REGISTRATION_CLOSED; no run is RUNNING; at least one active spot exists
    Main flow1. Check the idempotency key. 2. Refuse unless the period is REGISTRATION_CLOSED, no other period is in effect, and at least one bay is active — all three before any run row exists. 3. Draw and persist the seed, publish its commitment, and create the run in RUNNING (the insert is the lock). 4. Snapshot candidates and active bays against one frozen instant. 5. Compute every priority key (rules C, D, E, F). 6. Allocate in three passes — ACCESSIBLE, then EV, then STANDARD — each one sort, cut at the number of bays. 7. Persist assignments, waitlist, history and every priority key inside one transaction. 8. Mark run COMPLETED, cycle ACTIVE, emit AllocationCompleted. 9. Invalidate the caches, which may fail without failing the run.
    Alternate A1A run is already in flight → reject with 409 RAFFLE_IN_PROGRESS; no state change.
    Alternate A2Registrations ≤ spots → everyone wins; surplus spots stay available; waitlist empty.
    Alternate A3Zero registrations → run completes as COMPLETED_EMPTY; admin is notified; no fairness change.
    Exception E1Failure at any step → transaction rolls back, run marked FAILED with the error, lock released, nothing partially assigned.
    PostconditionsEvery registration has exactly one outcome row (ASSIGNED / WAITLISTED / SKIPPED); every entrant's priority key is stored with the run; the run is reproducible from its stored seed, input hash and result hash.

    UC-08 · Register for the raffle

    ActorResident
    PreconditionsAuthenticated; is_eligible = true; a cycle is in REGISTRATION_OPEN
    Main flowResident opens the dashboard → sees the open cycle and the closing date → confirms registration → system stores the registration and returns the projected fairness weight and current registrant count.
    AlternatesAlready registered → idempotent 200 with the existing registration. Ineligible → 403 NOT_ELIGIBLE plus the admin-supplied reason. Registration window closed → 409 REGISTRATION_CLOSED with the next cycle's opening date.
    PostconditionsOne registration row for (cycle, resident); resident's cached status invalidated.

    UC-09 · View current parking status

    ActorResident
    PreconditionsAuthenticated
    Main flowThe dashboard returns, in one call: current assignment (spot code, level, valid-until) or waitlist position; the next period's key dates; their waiting time and allocation count with a plain-language explanation; and the last four outcomes.
    NotesThis is the single hottest read in the system — it is what every resident opens. It is served from cache and invalidated by run completion, release and registration events (§20).

    Acceptance criteria — executable form

    Feature: Waiting-time allocation (rules A-F)

  Scenario: Fewer bays than registrants
    Given 50 registered residents
    And 30 active parking bays
    When the allocation run executes
    Then exactly 30 residents hold exactly one bay each
    And no bay appears in two assignments
    And the remaining 20 residents occupy waitlist positions 1..20
    And every one of the 50 has exactly one history row for this period

  Scenario: The longest wait wins, with no randomness involved
    Given resident A was made eligible 12 months ago and has never held a bay
    And resident B held a bay that ended 4 months ago
    When the run executes with 1 bay and only A and B registered
    Then A is assigned the bay
    And the result is the same for every seed      # the raffle is never reached

  Scenario: History breaks a tie on waiting time
    Given residents A and B have waited the same whole number of hours
    And A has held a bay once and B has held one three times
    When the run executes with 1 bay and only A and B registered
    Then A is assigned the bay
    And the result is the same for every seed

  Scenario: The raffle decides only an exact tie
    Given residents A and B have waited the same whole number of hours
    And both have held a bay the same number of times
    When the run executes with 1 bay and only A and B registered
    Then exactly one of them is assigned the bay
    And the winner is whichever has the lower sha256(seed:runId:residentId)
    And the same seed always produces the same winner

  Scenario: Early-Waiting Bias outranks even a first-time participant
    Given resident A has never participated and was made eligible 2 hours ago
    And resident B held a bay that ended 6 hours ago, inside the 24-hour window
    When the run executes with 1 bay and only A and B registered
    Then A is assigned the bay
    And B's stored effective waiting time is negative
    And B's stored bias_applied is true

  Scenario: The decision does not depend on input order
    Given any set of candidates and bays
    When the run executes twice with the same seed and the same decided-at instant,
         the second time with the candidate array shuffled
    Then both runs produce the same assignments, the same waitlist order
         and the same result hash

  Scenario: Concurrent triggers cannot double-allocate
    Given an allocation run is in progress
    When a second run is triggered for the same period
    Then it is rejected with error code RAFFLE_IN_PROGRESS
    And the number of assignments for the period is unchanged

  Scenario: A draw is refused while another period is still in effect
    Given a period is ACTIVE and its residents hold the bays
    When a run is triggered for the next period
    Then it is rejected with INVALID_CYCLE_STATE
    And no allocation run row is created       # a spurious run would strip
                                               # first-time status from everyone

  Scenario: Standing after the run
    Given resident A was assigned a bay and resident B was waitlisted
    When the run completes
    Then B's anchor is unchanged, so B's waiting time keeps growing
    And A's anchor moves only when A's bay stops counting as a benefit
    And no counter was written anywhere

  Scenario: A mid-run failure leaves nothing behind
    Given the persistence step fails after 12 of 30 assignments
    When the transaction aborts
    Then zero assignments exist for the period
    And the run status is FAILED with a recorded error
    And the run lock is released

    Architecture decision records

    ADRDecisionRejected alternativesWhy
    ADR-001Relational store as the source of truthDocument / key-value storeThe invariants that matter (one spot per resident per cycle, no partial runs) are multi-row and transactional. A unique constraint is a stronger guarantee than application code, and the data volume is trivially small.
    ADR-002Modular monolith, not microservicesService-per-moduleSix modules sharing one transaction boundary; the raffle would otherwise need a distributed transaction to stay correct. Module boundaries are enforced in code so a split later is mechanical.
    ADR-003Asynchronous notifications via an outbox + event busInline sending during the runSatisfies FR-24: a mail gateway outage must not roll back an allocation. Also keeps the run transaction short, which matters for lock hold time.
    ADR-004Delegated identity, token-basedHome-grown users/passwords tablePassword storage, reset flows and MFA are high-risk to build and free to rent. PACS stores a subject id, never a credential.
    ADR-005SPA client, static-hostedServer-rendered appThe product is an authenticated dashboard: no SEO need, no first-paint-critical public content. Static hosting also removes a whole tier from the ops surface.
    ADR-006Seeded, reproducible drawUnseeded RNGFairness that cannot be audited is only a claim. Storing the seed lets anyone replay a historical run and verify the outcome — the single strongest trust feature in the product.
    ADR-007Cache is read-only and disposableWrite-through / cache-as-storeEvery cached value is recomputable from the store. A cold cache costs latency, never correctness.
    ADR-008Logical design before cloud mappingDesigning against specific services from day oneKept the domain vendor-neutral and the comparison honest. The mapping is now made in §10 (ADR-011 … ADR-018); it lives only in the infrastructure ring, so it costs one adapter per platform seam.

    Cold start versus NFR-01

    A function that runs once a period is guaranteed to start cold (§20). Mitigation without paying for provisioned concurrency: a scheduler entry invokes runRaffle with a warmup payload before the real run, the bundle is tree-shaken and minified by esbuild, and AWS SDK clients are created lazily. The NFR-01 measurement (< 2 s) is taken on the warm invocation and the cold one is tracked as a separate metric.

    Reserved concurrency is not available on this account

    The original design reserved concurrency per function (api 10, jobs 1–2) to cap database connections. It cannot be deployed: the account's Lambda concurrency quota is 10, and AWS requires 10 to remain unreserved, so any reservedConcurrency value fails the stack. The quota does the same job by accident — at most 10 containers × a pg pool of 2 is 20 connections, comfortably inside a t4g.micro's budget. Each pool is created outside the handler and reused. RDS Proxy and Multi-AZ remain the production upgrade path, not a prerequisite for the pilot.

    12The Allocation Engine

    This is the component the whole product is judged on. Everything else is CRUD.

    This section was rewritten to match the code

    The design this document originally carried was a probabilistic weighted lottery: a fairness score s, a draw weight w = s + 1, and winners pulled from a Fenwick tree over those weights. That is not what was built. On 2026-10-05 the policy was settled as rules A–F, a deterministic ordering in which the raffle survives only as the last tie-break. The shipped engine is apps/api/src/modules/allocation/domain/ — priority-key.ts holds the rule, allocate.ts applies it — and the sections below describe that, not the earlier design. There is no fairness_state table, no stored score and no counter of misses anywhere in the schema.

    Rules A–F

    RuleWhat it saysWhere it lives
    AThe HOA configures the policy: how long an allocation lasts, how wide the early-waiting window is, the granularity at which two waits count as equal, and how many bays the scheme hands out. Every value is versioned, and a run stamps the version it usedallocation-config.ts
    BA resident takes part by registering while the period is REGISTRATION_OPEN. Not registering changes nothing about their standingcycle.ts, M-2
    CWaiting time is computed from timestamps, never stored. It is decidedAt minus an anchor, where the anchor is max(participationStartedAt, lastBenefitEndAt) — the instant waiting last restartedpriority-key.ts
    DHistorical allocation count breaks a tie on waiting time: fewer past allocations goes first. It is a lifetime count and is never resetpriority-key.ts
    EPriority is waiting time DESC → allocation count ASC → raffle. The raffle decides only among residents who are exactly equal on both of the first twocompareByPriority
    FEarly-Waiting Bias. A resident whose allocation ended within the last earlyWaitingBiasHours ranks below everyone whose wait is still running — including a resident taking part for the first timepriority-key.ts
    GLetting a bay go is a decision, and it is paid for. Both come back as warnings from configWarnings().

    The priority key

    Each candidate is reduced to a three-field key, computed once per run against one frozen instant. The key is persisted verbatim on allocation_run_candidate: it is the record a resident is entitled to contest, so it has to survive the run rather than be re-derived from data that has since moved.

    allocation/domain/priority-key.ts — the rule, exactly 
    // Rule G - a benefit ends when the period ends, when the bay is given back, when it is
// declined, or when the entry is withdrawn. All four are the resident holding, then not
// holding, something they asked for, so all four move the anchor and all four already
// count in servedCount.
benefitEnd    = max(lastBenefitEndAt, lastForfeitAt)        // either may be null

// Rule C, with H folded in - the anchor is the latest reset of any kind.
anchor        = max(participationStartedAt, benefitEnd, absenceResetAt)
rawWaitQuanta = max(0, floor((decidedAt - anchor) / waitQuantumMinutes))

// Rule F - a subtraction, not a comparison against the opponent. An absence reset does
// NOT make a resident cooling: they are back at zero, not fresh off a bay.
cooling       = benefitEnd !== null
                && 0 <= (decidedAt - benefitEnd) < earlyWaitingBiasHours
bias          = round(earlyWaitingBiasHours * 60 / waitQuantumMinutes)   // in whole quanta

effectiveWaitQuanta = rawWaitQuanta - (cooling ? bias : 0)

// Rule E - the raffle token. Derived from identity, never from array position, so a
// resident can recompute it with sha256sum and three strings.
raffleToken   = first 128 bits of sha256(seedHex + ":" + runId + ":" + residentId)

// Rule E - the total order.
compare(a, b) = b.effectiveWaitQuanta - a.effectiveWaitQuanta   // longer wait first
             || a.servedCount        - b.servedCount            // rule D: fewer first
             || a.raffleToken        - b.raffleToken            // the raffle
             || a.residentId         - b.residentId             // 128-bit collision guard

    rawWaitQuanta is clamped at zero deliberately: a clock that went backwards, or an administrator who types next month into the activation date, must not be able to mint priority out of nothing.

    Why rule F is arithmetic and not a second comparison

    Read naively, rule F is a statement about a pair of residents: "a cooling resident loses to a resident whose wait is running." Implemented that way it is not transitive — three residents can form a cycle in which A beats B, B beats C and C beats A, and a comparator with a cycle makes Array.prototype.sort implementation-defined. Two replays of the same run could then name different winners, which destroys the one property the whole design exists to provide.

    The shipped form avoids it: because a resident is cooling exactly while their raw wait is still inside the window, subtracting the whole window drives every cooling resident strictly negative and leaves everyone else at zero or above. Rule F's hard gate then falls out as a theorem of one candidate-local term, and the comparator is lexicographic over a product of total orders — transitive by construction. The non-transitive pairwise reading is pinned by a regression test in priority-key.spec.ts and must never be implemented.

    Why the raffle was demoted, and why it is still called a raffle

    requirements.pdf asks for spots to be rotated "via a raffle system", so the word stays in the UI, the API and the domain. What changed is its job. A raffle as the engine means a resident who has waited two years can lose to one who has waited two days, and no amount of weighting removes that — it only makes it less likely. Rules C and D remove it outright: the longest wait goes first, every time, and the raffle is reached only when two residents are indistinguishable on both waiting time and history. At a 60-minute quantum that is uncommon in a real building and routine in the first period, when nobody has waited any time at all.

    Execution flow

    The decision, in code

    One sort does everything. The raffle is not a separate step — it is the third field of the key — so rule E's "a raffle among only those residents of equal priority" cannot be got wrong: the cut line falls inside the tied group, and the tied group is already in uniformly random order.

    allocation/domain/allocate.ts — the three passes 
    const PASSES = [
  { name: 'ACCESSIBLE', admits: c => c.needsAccessibleSpot,  accepts: s => s.type === 'ACCESSIBLE' },
  { name: 'EV',         admits: c => c.hasElectricVehicle,   accepts: s => s.type === 'EV' },
  { name: 'STANDARD',   admits: () => true,                  accepts: () => true },
];

for (const pass of PASSES) {
  const ranked = candidates.filter(unassigned).filter(pass.admits)
                           .map(keyOf).sort(compareByPriority);
  // Which bay you get is not a lottery; only whether you get one is.
  const open   = spots.filter(untaken).filter(pass.accepts).sort(bySpotCode);

  for (let i = 0; i < min(ranked.length, open.length); i++) assign(ranked[i], open[i]);
}

    Restricted pools run first, which preserves BR-07 in both directions: a resident who loses a restricted pass falls through to the general pass with their key unchanged, and a restricted bay nobody claimed returns to the general pool — an empty accessible bay is worse than a standard-need resident parking in it. Non-winners keep the same order and the same tokens on the waitlist; there is no second raffle.

    Why not strict rotation, given it is the most even of the four

    Because the residents are not a fixed set. People move in and out, lose and regain eligibility, and skip periods.     Rules C and D answer it without a queue existing anywhere. There is no position to insert into: a resident is their timestamps and a count, so a newcomer's anchor is the day they were made eligible and both sort into the right place automatically.

    Rule H answers the returning resident outright, and it is the building's answer, not an inference from the data model: a resident who entered none of the last absenceResetPeriods periods comes back at zero. Absence no longer banks waiting time. The earlier text here said the knob was stored and wired to nothing, which was true until 2026-10-11 and is not any more — it is counted in periods now, and §31 states the whole rule.

    The arithmetic, stated exactly

    The priority of one candidate at one instant 
    benefitEnded    = max(lastAllocationEndedAt, lastWithdrawalAt)    // rule G
anchor          = max(madeEligibleAt, benefitEnded, absenceResetAt)
waitedHours     = floor((drawInstant - anchor) / 1 hour)          // clamped at 0
cooling         = benefitEnded is within the last 24 h
effectiveHours  = waitedHours - (cooling ? 24 : 0)

rank by:  effectiveHours  DESC     // longest wait first
          timesHeldABay   ASC      // rule D - never reset
          raffleToken     ASC      // sha256(seed : runId : residentId)

The first N in that order get the N bays. Nothing else is consulted, and the first
two keys are not random at all.

    Three properties worth stating because they are what residents actually ask about:

    • Nobody is ever stuck. Every period you do not win, your waiting time grows and everyone who did win drops to the bottom. Losing is not bad luck that might repeat; it is progress towards being first.
    • Nobody can game it. The only way to raise your priority is to wait while taking part. Holding a bay lowers it, letting one go lowers it by the same amount (rule G), sitting a period out sets it back to zero (rule H), and the raffle token is fixed by a seed whose hash is published before any candidate is read.
    • Nothing is hidden. A resident can be shown the integers that ranked them, and can recompute their own raffle token from the published seed with sha256sum.

    Rules the team holds to

    Events are facts, not commands

    Named in the past tense. A producer never knows or cares who consumes them, and never waits for a reply.

    Payloads carry ids, not PII

    Names, emails and plates stay in the database. A consumer that needs them reads them under its own permissions — so an event log is never a shadow copy of resident data.

    Additive versioning

    New optional fields do not bump version. Removing or retyping a field does, and both versions are published until every consumer has moved.

    Retry, then quarantine

    Five attempts with exponential backoff, then the message goes to a dead-letter queue that is alarmed. A poison message never blocks the queue behind it.

    The design rule behind those screens

    Never show a number without its sentence. "Waiting time: 4 350 h" means little to a resident; "you have been waiting 4 350 hours, longest wait goes first, and you have never held a bay, which breaks a tie in your favour" means everything. The API returns the explanation alongside the values precisely so the two can never drift apart — which is also why that explanation is still English-only and blocks Transloco (§10, §28).

    Rules G and H made the same demand twice more, and both are now met:

    • A clock that reads zero says why. A resident who sat a period out comes back to a waiting time of nothing. Shown bare, that number looks like a fault, and a number that looks like a fault gets reported as one. The dashboard reads the absence window exactly as the draw does and leads with the sentence: "You did not enter the last draw, so your waiting time started again from zero."
    • A cost is stated before it is incurred, not after. The withdraw and release dialogs now say that the action counts as a bay held and restarts the clock, and ask for confirmation against that. The release dialog previously said "Your score is not affected", which was false before rule G existed and is the kind of error only a resident reading their own history would ever catch.

    The genuine conflict, stated openly

    Append-only history (NFR-06) and the right to erasure pull in opposite directions. Deleting a resident's rows would silently change the historical record and break the reproducibility of past runs — the property the whole trust argument rests on. Pseudonymisation is the resolution: the run stays replayable and the row counts stay intact, while the person becomes unidentifiable. This needs sign-off from legal, and it is why the schema keeps identity in resident and never copies names into allocation_history.

    Privacy by design, as built

    Minimisation

    No phone number, no ID document, no date of birth, no employer. Every field in §11 is there because a use case needs it.

    No PII in transit sideways

    Domain events carry ids only. Logs carry ids only. A plate appears in a log line only masked.

    Purpose separation

    Plate observations, when they exist, live in their own store with their own access control — they are not joined into the allocation database by default.

    Access is logged

    An admin reading a resident's record writes an audit row. Curiosity is visible; that alone changes behaviour.

    Breach response

    1. Contain — revoke the compromised credential or key, rotate secrets, block the path.
    2. Assess — from the audit and access logs, determine exactly which records were reachable and whether they were read.
    3. Notify — the supervisory authority within 72 hours where the regime requires it, and affected residents without undue delay when there is real risk to them.
    4. Remediate and record — fix the cause, add the regression test, write the post-incident review. The review is blameless and is published to the team.

    The contact chain, notification templates and authority details belong in the runbook (§21) — written before they are needed, because nobody drafts a good breach notice at 2 a.m.

    Runbooks

    RB-01 · An allocation run failed

    Symptom. AllocationFailed event, run row in state FAILED with error_detail, cycle still REGISTRATION_CLOSED.

    What is already safe. The transaction rolled back: there are no partial assignments, and nobody's standing moved — waiting time is derived from timestamps, so there is no counter to roll back. Residents see "the draw has not run yet", which is true.

    1. Read error_detail and the logs for that runId.
    2. Confirm the blast radius: SELECT count(*) FROM spot_assignment WHERE cycle_id = … must be 0.
    3. Verify the lock is released — no row with state = 'RUNNING'. If there is one, go to RB-02.
    4. Fix the cause. The three seen in testing: no active spots (inventory error), a database connection drop (retry), a migration mid-flight (never deploy during the run window).
    5. Re-trigger with a new idempotency key. A new run row and a new seed are correct — the failed draw was never revealed to anyone.
    6. Confirm entrant and spot counts match expectations, then tell the admin it is done.

    Do not hand-insert assignments. The constraint set is the only thing keeping the invariants true, and a manual insert bypasses the fairness update.

    RB-02 · A run is stuck in RUNNING

    Symptom. A run has been RUNNING past the timeout; every new trigger returns 409 RAFFLE_IN_PROGRESS.

    Cause. The process died between claiming the lock and committing — the row survives, the worker does not.

    1. Confirm nothing is actually working: no active database session for that run, no recent log lines.
    2. Confirm no assignments exist for the cycle. If any exist, stop and escalate — this is RB-03.
    3. Mark the run failed, which releases the lock: UPDATE allocation_run SET state='FAILED', finished_at=now(), error_detail='reaped: worker lost' WHERE id=…
    4. Re-trigger as in RB-01.
    5. File a ticket: the reaper job that should have done this automatically did not, or does not exist yet.
    RB-03 · An allocation is wrong and must be reversed

    Symptom. A duplicate assignment, an ineligible winner, or a run executed against the wrong cycle. Rare, serious, and the one operation the system deliberately makes hard.

    Principle. We do not delete history. We record a correction, so the record shows both what happened and that it was put right.

    1. Freeze: set the cycle to a state that blocks further changes and tell the admin to announce a hold. Residents finding out from each other is worse than the error.
    2. Capture evidence: export the run, its assignments and its history rows before touching anything.
    3. Revoke the affected assignments through the normal admin path, with a reason — this emits AssignmentRevoked and writes audit rows.
    4. Decide with the HOA: re-run the whole cycle, or repair only the affected slots from the waitlist? Re-running changes outcomes for people who did nothing wrong, so prefer targeted repair.
    5. Correct fairness state explicitly: anyone whose outcome changed needs their score recomputed from history, not hand-edited.
    6. Communicate to every affected resident, naming what happened, why, and what changed for them.
    7. Post-incident review within a week; the regression test lands before the next cycle.
    RB-04 · Residents report the wrong status

    Symptom. "The app says I'm waitlisted but I got the email saying I won." Almost always a stale cache (R-05), not a wrong allocation.

    1. Check the source of truth first: query the assignment directly for that resident and cycle.
    2. If the database is right, it is a cache problem. Confirm with cache_hit_ratio and the invalidation logs for AllocationCompleted.
    3. Immediate fix: flush the affected dashboard:* keys. Data is recomputable, so this is safe.
    4. Root cause: find the path that changed data without emitting the event, and add the missing invalidation to the event handler — never as an ad-hoc call in a service method.
    5. If the database is wrong, this is RB-03.

    The raffle does not need to get faster — it needs to get smaller. Allocation is naturally partitioned by building: two buildings never compete for the same spot.     • Event sourcing — the append-only history already gives the audit trail that is the real requirement, without the operational weight.
    • Real-time push — polling on a dashboard is fine when state changes four times a year. Worth revisiting only alongside §24, where events are genuinely continuous.

    development is the default branch and master is the release line. Both are protected the same way: one approval, six required checks, conversation resolution, no force push. Feature branches are cut from development and merged back into it.

    The pipeline template is pipeline/dev/pipeline.yml (CloudFormation), and its three build stages are buildspec-build.yml, buildspec-deploy.yml and buildspec-smoke.yml beside it. Releasing is one command, deliberately — a merge never surprises the environment somebody is demonstrating on:

    Releasing to dev 
    aws codepipeline start-pipeline-execution --name pacs-development --region us-east-2

    Backend before frontend inside the deploy stage, because a frontend that went up first would be a new client calling an old server for the length of the deploy. In the S3 upload, hashed assets go first and index.html last, and it is the only file uploaded with no-store: the file that names every other file is the one that must never be cached. The artefact carries no node_modules — pnpm's symlinks into a content-addressed store do not survive a zip — so each stage installs from the same lockfile instead.

    What the Verify stage leaves behind

    Nothing an administrator can see, and that took work. The smoke suites create a period, a resident and a bay over real HTTP, then take them down through the API with the administrator's token: the period is deleted, the resident deactivated, the bay retired. Cognito test users are deleted on every run. Two inert rows survive — the deactivated resident and the retired bay — because removing them means reaching the database, which CodeBuild cannot: hotel-db's security group admits 5432 from one address and CodeBuild's changes every run. apps/api/scripts/clean-smoke-data.mjs clears them from a machine the group admits. The draw itself is not run in the pipeline: a committed run is a permanent record and would make the test period undeletable, so the write path is covered by the unit tests instead.

    Database migrations: expand, migrate, contract

    Five migrations exist, in apps/api/migrations, applied by node-pg-migrate with pnpm migrate:up from a developer machine. They are not in the pipeline, and that is the known gap: the database is reachable only from the single address its security group admits, so CodeBuild would be refused whatever credential it was given. The intended answer is a migrate Lambda inside the VPC that the deploy stage invokes.

    A migration file is not the schema

    1759600002000_waiting-time-fairness drops fairness_state in up and recreates it in down, so reading the CREATE TABLE in it describes the rollback and not the database. Read the live schema from information_schema before writing SQL against it.

    Migrations stay backward compatible for one release, so that a rollback does not meet a schema it cannot read.

    Renaming a column without downtime 
    Release N      EXPAND    add the new column, nullable; write to both; read the old
Release N+1    MIGRATE   backfill in batches; switch reads to the new column
Release N+2    CONTRACT  stop writing the old column; drop it

Rules
  · every migration has a tested down-script, or a documented reason it cannot
  · no migration runs inside the quarterly run window
  · batched backfills, never a single UPDATE over the whole table
  · rehearsed on a production-shaped copy before it runs for real

    Release checklist

    • Actions green on the exact commit being released — all six checks
    • Unit suites run locally before the commit (.githooks/pre-commit does it)
    • Migrations the commit needs applied by hand before the pipeline start, down-script verified
    • Verify stage green: smoke.mjs 41 and smoke-plates.mjs 28
    • No period currently in REGISTRATION_CLOSED awaiting a run
    • Changelog written in language the building admin can read
    • Rollback owner named and available for the next two hours
    • Smoke suite passing on staging against the same artefact — there is no staging
    • Feature flags for anything half-finished — none in the repository

    Rollback

    Rolling back today means releasing the previous commit: start the pipeline on it, which redeploys the backend with serverless deploy and re-syncs the bundle to S3. That is minutes, not a tagged artefact pulled from a registry — the pipeline builds from source each time, so "redeploy the previous immutable artefact" is a property this pipeline does not yet have. Schema stays put, which is what the expand/contract discipline buys. If a bad release wrote bad data, rolling back the code does not fix it: that is RB-03, and it is a different, slower procedure with human decisions in it.

    24Plate Recognition — M-7

    This was planned as a future module and then built

    This section used to open with "not built in phase 1". It is built: module apps/api/src/modules/plates, tables vehicle, plate_read, plate_config and access_event, Lambdas plateRecognizer and plateIngest, screens under features/plates and features/gate, and a 28-assertion smoke suite that runs in the pipeline's Verify stage. What is not built is the thing at the very front of the pipeline — a camera client — and the calibration that would make the thresholds mean something. Both are named at the end of this section rather than implied away.

    Capability, as shipped

    A camera at the garage entrance uploads a frame. The system reads the plate, matches it against the vehicle register, decides whether that vehicle may enter, and records the decision as an append-only event. A low confidence or an ambiguous match becomes a review item rather than a refusal, and a decision is never edited — it is overturned by inserting a new event that the old one points at.

    The decision table

    decide() takes the best candidate, the crop quality, the registered vehicles, whether the duplicate cooldown is active and the thresholds in force, and returns what to write. Every reason it can give is a stable code, never prose — the client owns the wording, which is the mistake the fairness explanation made and this module deliberately does not repeat.

    OutcomeReason codesWhat it means
    ALLOWEXACT_MATCH, FUZZY_MATCH_SINGLEOne registered, active vehicle matched, and its resident is eligible
    REVIEWFUZZY_MATCH_AMBIGUOUS, LOW_CONFIDENCE, UNREADABLE, MANUAL_REVIEWThe read is not good enough, or more than one vehicle could be meant. A human decides; nothing is refused automatically on a bad read
    DENYPLATE_NOT_REGISTERED, RESIDENT_NOT_ELIGIBLE, VEHICLE_INACTIVEThe read was good and the answer is no
    —DUPLICATE_WITHIN_COOLDOWNThe same plate again within the cooldown: discarded, so one car idling at the gate does not fill the log

    A plate read and an access decision are separate rows on purpose. A mis-read can be corrected without rewriting the access log, and a decision is overturned by inserting a new event that the old one points at through superseded_by — never by editing one.

    What phase 1 had already paid for

    GroundworkHow it was used
    vehicle table with a canonical plate, unique among active rowsThe join target for every recognition event. plate is the canonical form and plate_display is what the resident typed, so matching never depends on how somebody spaced it
    A query answering "does resident X hold a valid assignment right now?"The eligibility half of the decision, already indexed for UC-09
    Event outbox and stream fan-outReused unchanged. The plates pipeline added a filter, not a queue: without it plateIngest would wake for every Cognito and allocation event and pay for an RDS connection to discard it
    Plate treated as PII from day one (§18.4)Retention and masking were written before there was volume

    This is the one place where the original analysis paid off exactly as argued: the module was specified as future work, the schema and the async path were built so it would be cheap, and when it was built it needed no migration of existing data and no new infrastructure.

    Answers to the questions this section used to ask

    IDQuestionAnswer, as built
    Q-10Buy recognition or run our own model?Bought — Rekognition DetectText, 5 k images/month free for twelve months. Local-format knowledge lives in our code (bolivian-format.ts), not in the model
    Q-11Where does inference run?Cloud. There is no edge agent and no on-site gateway: the camera's only job is to upload a frame
    Q-12Are images retained, or only the decoded string?The frame is retained under a lifecycle rule and the decoded read is kept in plate_read. The per-plate crop is not written — see the gaps below
    Q-13What confidence threshold, and who reviews the rejects?Thresholds live in plate_config, so moving one is an UPDATE and not a deploy. An administrator reviews, on the features/plates screen. The numbers are not calibrated

    What is still missing

    • A capture client. POST /captures is the contract a gate camera would call for its presigned URL. No camera firmware and no web capture page is written, so in practice the pipeline is exercised by the smoke suite uploading a frame.
    • The plate crop writer. plate_read.crop_key, the crops/ IAM statement and the lifecycle rule all exist, but nothing writes a crop: cropping needs a native image decoder in the bundle, and the review screen reads the full frame instead.
    • Threshold calibration. The procedure and the storage exist; the week of shadow operation that produces real numbers has not happened, so 0.85 and 0.55 are a labelled starting point and nothing more.
    • A gate user in the pool. There is no CAMERA user by default; recreate it with pnpm --filter @pacs/api gate-user before testing the gate.
    • End-to-end coverage. Playwright covers sign-in and the admin screens; there is nothing for the gate.
    Privacy is the hard part, not the ML

    Continuous plate capture is surveillance of residents' movements. It needs a documented lawful basis, resident notice, a retention limit measured in days, strict access control on the event log, and an explicit decision that the data is never repurposed. Treat this as a compliance workstream running in parallel with the engineering one — not as a checkbox at the end. Nothing in the shipped module discharges this; the lifecycle rule on the bucket is a storage limit, not a privacy policy.

    CREATE EXTENSION IF NOT EXISTS citext;

CREATE TYPE spot_type        AS ENUM ('STANDARD','ACCESSIBLE','EV');
CREATE TYPE cycle_state      AS ENUM ('DRAFT','REGISTRATION_OPEN','REGISTRATION_CLOSED','ACTIVE','CLOSED');
CREATE TYPE run_state        AS ENUM ('RUNNING','COMPLETED','COMPLETED_EMPTY','FAILED');
CREATE TYPE assignment_state AS ENUM ('ACTIVE','RELEASED','REVOKED','EXPIRED');
CREATE TYPE waitlist_state   AS ENUM ('WAITING','PROMOTED','LAPSED');
CREATE TYPE outcome          AS ENUM ('ASSIGNED','WAITLISTED','SKIPPED');

CREATE TABLE resident (
  id                    uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  external_subject      varchar(255) NOT NULL UNIQUE,
  email                 citext       NOT NULL UNIQUE,
  full_name             varchar(200) NOT NULL,
  unit_number           varchar(30)  NOT NULL,
  is_eligible           boolean      NOT NULL DEFAULT true,
  ineligible_reason     varchar(280),
  needs_accessible_spot boolean      NOT NULL DEFAULT false,
  building_id           uuid         NOT NULL,            -- multi-building headroom (§22)
  created_at            timestamptz  NOT NULL DEFAULT now(),
  deactivated_at        timestamptz,
  CONSTRAINT uq_resident_unit_email UNIQUE (unit_number, email)
);

CREATE TABLE vehicle (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  resident_id   uuid NOT NULL REFERENCES resident(id),
  plate         varchar(16) NOT NULL UNIQUE,              -- normalised uppercase, no separators
  make          varchar(60),
  colour        varchar(30),
  registered_at timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE parking_spot (
  id             uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  spot_code      varchar(20) NOT NULL UNIQUE,
  level          varchar(20),
  type           spot_type   NOT NULL DEFAULT 'STANDARD',
  is_active      boolean     NOT NULL DEFAULT true,
  building_id    uuid        NOT NULL,
  notes          text,
  created_at     timestamptz NOT NULL DEFAULT now(),
  deactivated_at timestamptz
);

CREATE TABLE allocation_cycle (
  id                     uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  label                  varchar(20) NOT NULL UNIQUE,     -- '2026-01+3M', not a quarter
  building_id            uuid        NOT NULL,
  starts_on              date        NOT NULL,
  ends_on                date        NOT NULL,
  state                  cycle_state NOT NULL DEFAULT 'DRAFT',
  registration_opens_at  timestamptz NOT NULL,
  registration_closes_at timestamptz NOT NULL,
  CONSTRAINT ck_cycle_dates CHECK (ends_on > starts_on
                                   AND registration_closes_at > registration_opens_at)
);

CREATE TABLE raffle_registration (
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  cycle_id      uuid NOT NULL REFERENCES allocation_cycle(id),
  resident_id   uuid NOT NULL REFERENCES resident(id),
  registered_at timestamptz NOT NULL DEFAULT now(),
  withdrawn     boolean     NOT NULL DEFAULT false,
  -- Rule G. The boolean answers "are they in this draw", which re-registering flips
  -- back; the timestamp answers "did they once take a bay off the board and hand it
  -- back", which nothing ever clears. Only the second one decides anything about
  -- fairness, and it is what both the clock reset and the +1 are read from.
  withdrawn_at  timestamptz,
  CONSTRAINT uq_registration_per_cycle UNIQUE (cycle_id, resident_id)
);

-- Rule G's lookup is per resident and ignores the period: every withdrawal this
-- resident has ever made, newest first.
CREATE INDEX ix_registration_forfeit ON raffle_registration (resident_id, withdrawn_at DESC)
  WHERE withdrawn_at IS NOT NULL;

CREATE TABLE allocation_run (
  id                uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  cycle_id          uuid       NOT NULL REFERENCES allocation_cycle(id),
  state             run_state  NOT NULL DEFAULT 'RUNNING',
  random_seed       bigint     NOT NULL,
  algorithm_version varchar(40) NOT NULL,
  idempotency_key   varchar(120) NOT NULL UNIQUE,
  entrants_count    int, spots_count int, assigned_count int,
  started_at        timestamptz NOT NULL DEFAULT now(),
  finished_at       timestamptz,
  error_detail      text
);
-- the run lock: at most one RUNNING row in the whole table
CREATE UNIQUE INDEX uq_single_running_run ON allocation_run ((state)) WHERE state = 'RUNNING';

CREATE TABLE spot_assignment (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  cycle_id    uuid NOT NULL REFERENCES allocation_cycle(id),
  run_id      uuid NOT NULL REFERENCES allocation_run(id),
  resident_id uuid NOT NULL REFERENCES resident(id),
  spot_id     uuid NOT NULL REFERENCES parking_spot(id),
  state       assignment_state NOT NULL DEFAULT 'ACTIVE',
  valid_from  timestamptz NOT NULL,
  valid_until timestamptz NOT NULL,
  released_at timestamptz,
  CONSTRAINT uq_one_spot_per_resident_per_cycle UNIQUE (cycle_id, resident_id),
  CONSTRAINT uq_one_resident_per_spot_per_cycle UNIQUE (cycle_id, spot_id)
);

CREATE TABLE waitlist_entry (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  cycle_id    uuid NOT NULL REFERENCES allocation_cycle(id),
  run_id      uuid NOT NULL REFERENCES allocation_run(id),
  resident_id uuid NOT NULL REFERENCES resident(id),
  position    int  NOT NULL,
  state       waitlist_state NOT NULL DEFAULT 'WAITING',
  CONSTRAINT uq_waitlist_position UNIQUE (cycle_id, position),
  CONSTRAINT uq_waitlist_resident UNIQUE (cycle_id, resident_id)
);

CREATE TABLE allocation_history (
  id                    uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  run_id                uuid NOT NULL REFERENCES allocation_run(id),
  cycle_id              uuid NOT NULL REFERENCES allocation_cycle(id),
  resident_id           uuid NOT NULL REFERENCES resident(id),
  spot_id               uuid REFERENCES parking_spot(id),
  result                outcome NOT NULL,
  fairness_score_at_draw numeric(6,2),            -- legacy, nullable, never written now
  waitlist_position     int,
  recorded_at           timestamptz NOT NULL DEFAULT now()
);
REVOKE UPDATE, DELETE ON allocation_history FROM app_user;   -- append-only (BR-05)

-- Rule A. Append-only: a run points at the version in force when it ran, so changing
-- the policy tomorrow cannot rewrite why somebody lost today.
CREATE TABLE allocation_config (
  version                  int GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  allocation_duration_months int NOT NULL DEFAULT 3  CHECK (allocation_duration_months BETWEEN 1 AND 60),
  early_waiting_bias_hours   int NOT NULL DEFAULT 24 CHECK (early_waiting_bias_hours BETWEEN 0 AND 8760),
  wait_quantum_minutes       int NOT NULL DEFAULT 60 CHECK (wait_quantum_minutes >= 1),
  -- Rule H, counted in periods rather than months: that is the unit the rule is stated
  -- in and the only one a resident can act on. NULL disables the reset.
  absence_reset_periods      int DEFAULT 1 CHECK (absence_reset_periods IS NULL OR absence_reset_periods >= 1),
  total_bays                 int NOT NULL DEFAULT 0  CHECK (total_bays >= 0),
  changed_by               uuid REFERENCES resident(id),
  changed_at               timestamptz NOT NULL DEFAULT now()
);

-- The contestable record: one row per entrant per run, holding the key that ranked them.
-- This is what replaced the fairness-score table - see §11 and §12.
CREATE TABLE allocation_run_candidate (
  run_id                uuid NOT NULL REFERENCES allocation_run(id),
  resident_id           uuid NOT NULL REFERENCES resident(id),
  anchor_at             timestamptz NOT NULL,          -- rule C
  raw_wait_quanta       bigint NOT NULL CHECK (raw_wait_quanta >= 0),
  effective_wait_quanta bigint NOT NULL,               -- negative exactly while cooling
  bias_applied          boolean NOT NULL,              -- rule F
  first_time            boolean NOT NULL,
  served_count          int NOT NULL,                  -- rule D
  raffle_token          numeric(39,0) NOT NULL,        -- 128-bit, as decimal
  final_rank            int NOT NULL CHECK (final_rank > 0),
  pool                  text,                          -- ACCESSIBLE | EV | STANDARD
  outcome               outcome NOT NULL,
  spot_id               uuid REFERENCES parking_spot(id),
  PRIMARY KEY (run_id, resident_id)
);
REVOKE UPDATE, DELETE ON allocation_run_candidate FROM app_user;  -- append-only

CREATE TABLE outbox (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  event_id    varchar(40) NOT NULL UNIQUE,
  type        varchar(60) NOT NULL,
  version     int         NOT NULL DEFAULT 1,
  payload     jsonb       NOT NULL,
  status      varchar(10) NOT NULL DEFAULT 'NEW',
  attempts    int         NOT NULL DEFAULT 0,
  created_at  timestamptz NOT NULL DEFAULT now(),
  sent_at     timestamptz
);
CREATE INDEX ix_outbox_pending ON outbox (created_at) WHERE status = 'NEW';

CREATE TABLE audit_log (
  id          bigserial PRIMARY KEY,
  actor_id    uuid,
  actor_role  varchar(20) NOT NULL,
  action      varchar(60) NOT NULL,
  subject     varchar(120),
  before      jsonb, after jsonb,
  reason      varchar(280),
  trace_id    varchar(40),
  at          timestamptz NOT NULL DEFAULT now()
);

-- hot-path indexes (§11)
CREATE INDEX ix_registration_cycle      ON raffle_registration (cycle_id) WHERE withdrawn = false;
CREATE INDEX ix_spot_assignable         ON parking_spot (type) WHERE is_active = true;
CREATE INDEX ix_assignment_resident_now ON spot_assignment (resident_id, state) WHERE state = 'ACTIVE';

    31The Rules, in Full

    Every rule that decides who parks, stated once, with the arithmetic and a worked example for each. This is the section to hand to a resident who asks why, and the section to check an implementation against.

    Why this section exists separately

    §12 explains the engine to somebody who will maintain it and §13 argues the policy against the alternatives. Neither is the thing a resident, an administrator or a reviewer actually asks for, which is the rules themselves, in order, with nothing between them. Rules A–F were settled on 2026-10-05; G and H on 2026-10-11, after the first model had already run. All eight are in the deployed code.

    The whole policy on one page

    RuleIn one sentenceEffect on the clockEffect on the count
    AThe building configures the policy, and every version is kept——
    BYou take part by entering that period's draw; nothing is automatic——
    CWaiting time is measured from the last reset, not counted upthe clock is this rule—
    DFewer bays held breaks a tie on waiting time—the count is this rule

    Two sentences carry the whole design, and everything below is detail:

    Waiting time decides. The count breaks ties. The raffle breaks what is left.
    Waiting only accrues while you are taking part, and letting a bay go costs what holding one costs.

    Rule A — the building sets the policy

    Four numbers, set by the administrator, versioned on every change. A draw stamps the version it ran under, so changing a number today cannot rewrite why somebody lost last year.

    SettingDefaultWhat it decides
    Period length3 monthsHow long an allocation lasts, and the name of the period. Nothing in the code assumes a quarter
    Early-waiting window24 hoursRule F's window. 0 switches rule F off
    Wait quantum60 minutesThe granularity at which two waits count as equal — and so how often the raffle is reached at all
    Absence reset1 periodRule H's window. Off means absence never costs the clock
    Bays allocatedevery active bayA cap, if the building wants to hold some back

    Example. Set the wait quantum to a full day and most residents end up tied on waiting time, so the raffle decides nearly everything — the policy quietly becomes the lottery it was designed to replace. The system does not refuse the value; it warns, because it is legal and might be intended.

    Rule B — you are in a draw because you entered it

    There is no standing entry and no automatic renewal. Each period opens a registration window, and a resident who wants a bay enters during it. Administrators never enter: they operate the draw.

    Not entering is not a penalty in itself — but see rule H, which is what makes it cost something.

    Example. R4 holds a bay in the period now running and wants one for the next period too. It must enter the next draw like everybody else. Holding a bay now grants nothing later, and in fact rule C will have it start the next draw at zero.

    Rule C — waiting time is a subtraction, never a counter

    Your waiting time is the moment of the draw minus your anchor. The anchor is the last instant your waiting restarted. Nothing is stored and nothing is incremented, so there is no number anywhere that can drift, be missed by a failed job, or be quietly edited.

    The anchor, which is the whole of rule C 
    anchor = the LATEST of:
           · the day you were made eligible                      (you have never held a bay)
           · the end of your last allocation                     (rule C)
           · the moment you withdrew, declined or gave one back  (rule G)
           · the entry that ended an absence                     (rule H)

waitingTime = drawInstant - anchor            clamped at zero, measured in whole quanta

    Because the anchor is a maximum, the question "which reset wins when two apply" always has the same answer: the most recent one. That is what lets rules C, G and H be stated separately without any of them contradicting another.

    Example. R6's bay ended 30 September. It skipped the next period and re-entered on 20 December. Two resets apply — the bay ending, and the re-entry — and the later one wins, so R6 enters the January draw with the hours since 20 December, not the hours since September.

    The clamp at zero is not decoration

    An administrator who mistypes an activation date as next month would otherwise hand that resident a negative wait, which sorts above everyone. The clamp means the worst a bad date can do is give somebody zero waiting time, which is the same as arriving today.

    Rule D — how many bays you have held, for life

    A count of allocations that counted. It breaks a tie on waiting time: fewer goes first. It is never reset — not by an absence, not by moving out and back, not by anything. It is the only part of a resident's standing that remembers more than one reset ago.

    What adds one, in every case: a bay held to the end of the period, a bay given back early, a bay lost for cause, a bay declined, and an entry withdrawn. What does not: an administrative cancellation the administrator explicitly marks as the system's error.

    Example. R3 and R8 both enter with 4 398 hours waited. R3 has held one bay, R8 has held two. R3 goes first, and no raffle is involved — the tie was broken before the raffle was reached. If both had held one, the raffle would decide.

    Rule E — the order, and where the raffle actually sits

    Sort every entrant by this, then hand out the bays from the top 
    1.  waiting time      DESCENDING     longest wait first
2.  bays held         ASCENDING      fewest first
3.  raffle token      ASCENDING      sha256(publishedSeed : drawId : residentId)
4.  resident id                      a guard against a 1-in-2^128 collision, never reached in practice

    The raffle is the third key, not a separate step. That ordering is what makes "a raffle among those of equal priority" impossible to get wrong: the cut-off line falls inside the tied group, and the tied group is already in random order.

    The token is derived from the published seed, the draw's id and the resident's id — never from position in a list, which would be a hidden alphabetical bias. The seed's hash is published before the entrants are read, so re-rolling for a nicer result is a hash-preimage problem rather than an operational one. Any resident can recompute their own token with sha256sum and three strings.

    Example. Three bays, and the top of the order reads: R7 (4 422 h), R1 (4 422 h), R5 (2 214 h, one bay held), R6 (2 214 h, two bays held). R7 and R1 are tied on waiting time and on history, so their raffle tokens order them — but both get a bay regardless, so the raffle changed nothing. R5 beats R6 on rule D. The raffle only ever matters when the cut-off line falls inside a tied group.

    Rule F — nobody wins twice in a row by accident

    A resident whose bay ended within the last 24 hours ranks below everybody whose wait is still running — including somebody taking part for the first time. The window is configurable; the default is a day.

    Without it, a draw held immediately after a period ends would be a coin-toss between the people who just had a bay and the people who have been waiting, because both groups would show roughly zero waiting time.

    Why it is a subtraction and not a comparison

    Read as a statement about a pair of residents — "the cooling one loses to the waiting one" — rule F is not transitive: three residents can form a cycle where A beats B, B beats C and C beats A. A sort with a cycle in its comparator has an implementation-defined result, so two replays of the same draw could name different winners, which destroys the one property the design exists to provide.

    So it is implemented as arithmetic on the resident's own key: the whole window is subtracted, which drives every cooling resident below zero and leaves everybody else at zero or above. The hard gate then follows as a consequence rather than as a second comparison. The pairwise version is pinned by a regression test and must never be implemented.

    Example. R3's bay ended six hours before the draw. Its raw wait is 6 hours; the window is 24, so its effective wait is −18 and it is last. Eighteen hours later the window closes and the same 6 hours counts as 24 — an ordinary, positive wait, and R3 is back in the order like everyone else.

    Rule G — letting a bay go costs what holding one costs

    Settled 2026-10-11.

    Three different acts, one outcome:

    What the resident doesWhenCountClock
    Enters, then withdrawsbefore the draw+1restarts at the withdrawal
    Wins a bay, then declines itafter the draw, at any speed+1restarts at the decline
    Gives a held bay backany time in the period+1restarts at the handover
    Holds it to the end—+1restarts when the period ends

    The principle: entering a draw is asking for a bay, and taking it back is a decision about a bay. The system does not distinguish between the ways of making that decision, and there is no free window for any of them.

    There used to be a free window, and removing it was the point

    Declining a bay you had won used to be free within 48 hours. Next to rule G that is incoherent: the resident who withdrew before the draw — and never took a bay off the board at all — would pay more than the one who won a bay, sat on it for a day and handed it back. It also created the obvious manoeuvre: rather than withdraw, let yourself win and decline. The window is gone, and declineGraceHours no longer exists in the configuration, the database or the admin screen.

    What was given up with it: a resident who cannot use a bay now pays to say so. The counter-argument was that a free decline keeps bays from sitting empty. It did not survive — the bay goes to the waitlist either way, so the building loses nothing, and only the resident's own standing is affected.

    Example. R8 wins a bay in October, hands it back on 2 November because it is moving out for a month, and enters the January draw. It has two marks against it: the count went up by one when it handed the bay back, and its clock runs from 2 November rather than from the September before. If instead it had held the bay to 31 December, the count would be the same and the clock would run from 31 December — worse. Giving a bay back early is still the better move; it buys waiting time, one day for one day. What it does not buy is a clean record.

    Re-entering does not undo it. A resident who withdraws and then enters again while the window is still open is in the draw — but the withdrawal stays on the record and the clock stays restarted. The are you in this draw question and the did you once hand a bay back question are stored separately, and only the second decides anything.

    Rule H — sitting a period out restarts the clock

    Settled 2026-10-11.

    A resident who enters none of the last N periods comes back with their waiting time at zero, measured from the entry that brings them back. N defaults to 1: miss one draw and the clock goes. The count is untouched.

    The problem it solves: without it, absence banks waiting time. Somebody who ignores the building's draws for two years returns with two years of accrued waiting and goes straight to the front, ahead of everyone who turned up every time. Waiting time is meant to measure waiting, and somebody who was not in the queue was not waiting.

    ConditionWhy it is there
    Entered none of the last N periodsThe rule itself. Entering and then withdrawing counts as entering — that is rule G's business, and it has already been paid for
    Could have entered the oldest of themA resident who moved in last month did not miss anything. Nobody is charged for the building's history before they arrived
    There have been N periods to missIn a building on its second ever period, nobody has had the chance. The rule waits until it can be fair

    The new clock starts at the entry, not at the start of the period, and that is deliberate: it is the act of re-joining that is being measured, and it is the one instant the resident controls.

    What rule H deliberately does not do
    • It does not touch the count. Skipping a period cannot be used to wash a history clean. A resident who has held three bays and sits out a year comes back with zero waiting time and still three bays against them in every tie.
    • It does not make the returning resident "cooling" under rule F. They are at zero, not fresh off a bay. A returning resident sorts below everyone who has been waiting and above anyone who has not — which is exactly where somebody who just arrived belongs.
    • It does not punish absence twice. Missing four periods costs the same as missing one: the clock, once. There is nothing further to take.

    Example. R2 held a bay that ended 30 September, lost the October draw, then did not enter the January draw at all. It enters again in April. Without rule H it would arrive with about 5 100 hours — more than anyone — and take a bay immediately. With rule H it arrives with the hours since it re-entered, somewhere in the low hundreds, and waits its turn behind everyone who kept entering. Its history still reads one bay held, so if it does reach a tie, it wins it.

    The waitlist, which is not a separate rule

    It is the same order, continued below the cut-off. If there are 50 bays and 80 entrants, the first 50 are assigned and the other 30 are recorded as the waitlist in the order they already had. There is no second draw and no second raffle — the tokens are the ones from the first.

    • It exists to fill bays that come free during that period. If somebody gives a bay back, the top of the waitlist takes it for whatever is left of the period.
    • It does not carry over. Being 51st this period grants nothing next period. What carries is the clock: a resident who was not assigned keeps accruing waiting time, which is what puts them above the period's winners next time anyway.
    • Taking a bay from the waitlist is holding a bay. When it ends, the count goes up and the clock restarts, exactly as for anyone else.

    Example. 80 residents, 50 bays. After the first draw, 50 hold bays and 30 are on the waitlist. Three months later every one of those 50 arrives at the next draw with a clock of zero, and all 30 of the waitlisted arrive with a full period of waiting. The 30 take bays first — not because the waitlist carried over, but because they waited and the others did not.

    What a resident is entitled to be told

    Every number a resident is shown arrives with the sentence that explains it, from the same source, so the two cannot drift apart. After a draw, their row is kept exactly as it was computed — anchor, raw wait, effective wait, count, token, final rank — because that row is what they are entitled to contest, and re-deriving it later from data that has since moved would not be the same thing.

    • Before the draw: their waiting time, their count, and what either would need to be for them to be first.
    • When the clock reads zero because of rule H: that it was the absence that did it. A bare zero looks like a fault, and anything that looks like a fault gets reported as one.
    • Before withdrawing or giving a bay back: what it will cost, stated before they confirm rather than discovered afterwards.
    • After the draw: where they ranked, how many people were ahead, and whether the raffle was reached at all — and if it was, the seed and the three strings to recompute their own token.
    Three claims the policy is prepared to defend
    • Nobody is ever stuck. Every draw you enter and lose, your waiting time grows and the winners drop below you. Losing is not luck that might repeat indefinitely; it is progress towards being first.
    • Nobody can game it. The only way up is to wait while taking part. Holding a bay resets you, letting one go resets you and marks your record, sitting out resets you, and the raffle token is fixed by a seed whose hash was published before the entrants were read.
    • Nothing is hidden. Every input is a date or a count the resident can see, and the only random number in the system is one they can recompute themselves.
